# 1단계: 시스템 선택과 입력 검증

이번 단계의 목적은 **사용자가 선택한 시스템만 조회하는 것**이다.
사용자는 시스템을 선택하고 증상을 자연어로 입력한다. 정해진 접수 양식은 필요 없다.

예를 들어 `auth-service`를 선택하고 “로그인 후 화면이 넘어가지 않아요”라고 입력하면,
질문에 “장애”라는 단어가 없어도 해당 시스템의 샘플 상태를 조회한다.

## 파일별 추가·수정 내용

| 구분 | 파일 | 바뀐 내용과 이유 |
|---|---|---|
| 추가 | `agent/system_catalog.py` | `data/monitoring.json`에서 시스템 목록을 읽고 선택값을 검증한다. 파일이 없거나 손상되면 임의의 목록으로 대체하지 않는다. |
| 수정 | `server.py` | `GET /systems`와 `ChatRequest.selected_system`을 추가했다. 질문·대화 ID의 공백 입력과 미등록 대상을 검증한다. 일반 응답과 스트리밍이 같은 입력 규칙·초기 상태를 사용한다. |
| 수정 | `agent/graph.py` | 선택값이 있으면 LLM의 분류·계획을 건너뛰고 선택 대상 조회 작업 하나를 만든다. 실제 도구 호출 직전에도 대상이 일치하는지 검사한다. |
| 수정 | `web_demo_server.py` | 목록과 선택값을 백엔드에 전달한다. 백엔드의 입력 오류를 정상 스트리밍 응답으로 감추지 않고 그대로 반환한다. 연결 오류 안내와 연결 정리도 추가했다. |
| 수정 | `web_chat.html` | 시스템 선택창, 샘플 데이터 안내, 목록 재시도, 오류 메시지를 추가했다. 선택하지 않거나 질문이 공백이면 전송할 수 없다. 질문마다 선택했던 대상을 화면에 남긴다. |
| 추가 | `tests/test_selected_system.py` | API와 그래프에서 선택 대상만 조회하고 잘못된 요청을 차단하는지 검증한다. |
| 추가 | `tests/test_web_proxy.py` | 중계 서버가 선택값·오류 응답·스트림을 올바르게 전달하는지 검증한다. |

코드의 한국어 주석은 “무엇을 하는지”와 함께 **왜 이 검사가 필요한지**를 설명한다.
읽는 순서는 `system_catalog.py` → `server.py`의 `ChatRequest`·`_initial_state` →
`graph.py`의 `route_node`·`plan_node`·`research_node` → 프록시 → 화면을 권장한다.

## 기존 동작에서 달라진 점

| 상황 | 기존 | 시스템 선택을 사용하는 새 흐름 |
|---|---|---|
| “로그인 후 화면이 넘어가지 않아요” | 모델의 분류에 따라 일반 대화로 처리될 수 있음 | 선택한 시스템의 기초 점검으로 진행 |
| 조회 대상 결정 | 질문에서 추측하거나 기본 대상 사용. fake 계획은 `web-01`도 추가 | 사용자가 선택한 시스템 하나만 조회 |
| 질문에 다른 시스템 이름도 포함 | 계획에 다른 시스템이 포함될 수 있음 | 선택창의 대상이 기준. 다른 시스템을 보려면 선택을 변경 |
| 공백 질문·대화 ID | 별도 공백 검증 없음 | 요청 시작 전에 HTTP 422 |
| 알 수 없는 선택값 | 선택값 필드 없음 | 요청 시작 전에 HTTP 422. 다른 시스템으로 바꾸지 않음 |
| 정상·unknown 상태 또는 매뉴얼 매칭 근거 없음 | 기본 `db-down` 매뉴얼을 선택할 수 있음 | 매뉴얼 조회를 생략하고 그 이유를 진행 기록에 표시 |
| 백엔드 연결 실패 | 화면에서 조용히 종료될 수 있음 | 오류 안내 표시, 다시 전송할 수 있도록 상태 복구 |

**화면에서는 시스템 선택이 필수다.** 기존 실습용 API와의 호환성을 위해 API에서
`selected_system`을 생략하거나 JSON `null`로 보내면 기존 자유 대화·진단 경로를
사용한다. 이 기존 경로에는 대상 추측 등의 실습 동작이 남아 있다.
빈 문자열(`""`)은 생략으로 처리하지 않고 오류로 반환한다.

선택 기능은 `SUPERVISOR_VERSION=v2`에서 지원한다. `v1`에서 선택값을 보내면
선택을 무시하는 대신 HTTP 409를 반환한다.

## 요청부터 답변까지

1. 화면이 `GET /systems`로 등록 목록을 가져온다. 기본으로 선택된 시스템은 없다.
2. 사용자가 시스템을 고르고 증상을 입력한다.
3. 화면 → 프록시 → 백엔드로 `selected_system`, `message`, `thread_id`가 전달된다.
4. 서버가 입력을 검증한다. 스트리밍도 연결을 열기 전에 검증한다.
5. 그래프가 선택 대상의 모니터링 작업 하나를 만들고 MCP 도구로 조회한다.
6. 수집된 이상 상태와 알림이 기존 규칙에 맞으면 관련 매뉴얼을 조회한다.
7. 기존 답변 작성·검수 흐름으로 답변한다. 최종 응답에는 선택 대상과 `data_source: "sample"`을 포함한다.

현재는 `data/monitoring.json`과 기존 매뉴얼을 사용한다. 실제 운영 로그·지표와
연결한 것이 아니므로 사용자 증상의 실제 원인이 확인된 것은 아니다.
매뉴얼 선택도 여전히 키워드 규칙이며, 임베딩·벡터 검색을 사용하는 RAG는 다음 단계다.

## API 예시

시스템 목록:

```http
GET /systems
```

```json
{
  "systems": ["auth-service", "web-01", "payments-service", "cache-service", "gateway-service", "log-service"],
  "data_source": "sample"
}
```

일반 응답:

```http
POST /chat
Content-Type: application/json
```

```json
{
  "message": "로그인 후 화면이 넘어가지 않아요",
  "thread_id": "helpdesk-demo",
  "selected_system": "auth-service"
}
```

스트리밍은 동일한 필드를 `GET /chat/stream`의 쿼리 매개변수로 전달한다.
일반 응답의 `metadata`와 SSE의 `FinalAnswer`에는 선택한 시스템과 샘플 출처가 포함된다.

## 실행·확인 방법

가상환경과 의존성이 준비되어 있다면, 프로젝트 루트에서 두 터미널로 실행한다.
아래 백엔드 명령은 `.env`를 읽지 않고 fake 모델을 사용하므로 외부 LLM API를 호출하지 않는다.
기존 포트를 사용하는 서버가 있다면 먼저 해당 프로세스를 정상 종료한다.

```bash
# 터미널 1: 백엔드. 실행 스크립트의 DB 초기화 절차를 거치지 않고 직접 시작한다.
PYTHON_DOTENV_DISABLED=1 LANGSMITH_TRACING=false LANGCHAIN_TRACING_V2=false LLM_BACKEND=fake SUPERVISOR_VERSION=v2 .venv/bin/python server.py
```

```bash
# 터미널 2: 화면 중계 서버
.venv/bin/python web_demo_server.py
```

`http://localhost:8600`에서 시스템을 선택하고 증상을 입력한다.
진행 기록의 모니터링 대상이 선택한 시스템 하나인지 확인한다.
`web-01`은 샘플 상태가 정상이라 장애 매뉴얼 조회를 생략하는 예시다.

자동 테스트:

```bash
.venv/bin/python -m unittest discover -s tests -v
```

테스트는 외부 모델·운영 서버 대신 테스트용 MCP 응답과 임시 DB를 사용한다.
기존 `.env`의 키와 프로젝트의 `session.db`를 사용하지 않는다.

## 다음 단계와 현재 범위

- 현재 선택값은 요청·응답·화면에 포함된다. DB는 기존 대화 메시지 저장 구조를 사용하며, 선택값을 별도 접수 항목으로 저장하는 기능은 아직 없다.
- 발생 시각·오류 메시지 등 누락 정보를 물어보는 기능과 관리자용 접수 요약은 이후 단계에서 추가한다.
- RAG는 사내 FAQ·매뉴얼을 검색하고 출처를 함께 제시하는 단계로 추가한다.
- 실제 로그·모니터링 연동과 관리자 알림 전송은 아직 구현하지 않았다.
