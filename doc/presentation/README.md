## 최신 실제 화면과 검증

9~14장과 19장은 기능 커밋 **`ba5a883`**를 별도 폴더·포트·임시 DB에서 실행한
[최신 템플릿 발표용 근거](../evidence/template_final_20261021/README.md)를 사용했다.
기존 8100/8600 서버와 실제 대화 DB는 변경하지 않았다. 화면의 답변이나 DOM을 바꾸지 않았고,
부분 확대도 실제 화면·요소를 사용했다.

- 모델: 문의 정리 `qwen3:0.6b`, 답변 생성 `qwen3:8b`, 임베딩 OpenAI `text-embedding-3-small`.
- 합성 문의: “오전 9시부터 로그인 후 화면이 넘어가지 않아요. 오류 메시지는 없어요. 윈도우 크롬을 사용해요.”
- 최종 촬영 문의의 UI 검사 **10/10 통과**. 모델이 네 접수 항목을 추출했으며 `source=model`, 경고 0이었다.
- 최종 답변은 규칙 검증을 통과했고 `faq:login`·`faq:browser`를 인용했다. 미확인 504 안내와 내부 JSON 항목명 표시는 없었다.
- 새로고침 후 같은 접수 ID·선택 대상·답변을 복원했고, 관리자 상세와 일치함을 확인했다. 페이지 JavaScript 오류 0.
- 자동 검사 **217개 테스트 + 173개 하위 검사 통과**, 실패·오류·건너뜀 0. 모의 의존성을 포함한 회귀 검사이며 실제 LLM 진단 정확도 측정이 아니다.
- LangSmith 원격 조회에서 최종 촬영 요청의 **하위 실행 30개**, 루트 오류 없음, 코드·모델·문의 식별자 일치를 확인했다.

| 시간 범위 | 최종 촬영 문의의 단일 관측값 |
|---|---:|
| 브라우저 클릭부터 응답 완료 | 48.392초 |
| 앱 실행부터 DB 저장 직전 | 48.194초 |
| LangSmith 루트 실행 | 48.211초 |

시간 범위는 서로 다르며 부모·자식 실행 시간은 겹치므로 더하지 않는다. 기존 시연의 약
52.49초·하위 실행 31개와 비교해 속도가 개선됐다고 주장하지 않는다. 첫 촬영 자동화는
완료 대기 조건 오류로 시간 초과했지만 앱 요청은 정상 완료했다. 그 자료도 보존했으며,
조건을 고친 뒤 같은 합성 문의를 새 접수로 한 번 더 전송해 최종 화면을 확보했다.

13장은 **1차 근거 검증을 적용한 뒤에도 남았던 504 안내 문제**와 후속 보완을 설명한다.
확인하지 않은 HTTP 오류 코드(4xx/5xx)가 든 문서는 답변 작성 근거에서 제외하고, 최종 답변도
같은 규칙으로 검사한다. 검색 원본에는 해당 문서가 남아 관리자·사용자 검색 결과에 표시될
수 있다. 규칙 통과가 모든 안내의 의미나 원인의 타당성을 보장하지는 않는다. 실제 답변에
남은 해석상의 한계도 [최신 실행 기록](../evidence/template_final_20261021/README.md)에 보존했다.
이번 입력은 네 필드가 모두 있으므로 추가 질문 경로는 이전 단계 근거와 회귀 검사로 확인한다.

## 전후·공급자 비교를 읽는 기준

- **16장 — 같은 문의의 서비스 화면:** 원본 `ee32f7e`와 6단계 완료본 `19bacc0` 모두
  fake 생성 모델을 사용했다. 질문은 “로그인 후 화면이 넘어가지 않아요. 오류 메시지는
  없어요.”로 같고, 개선본에는 `auth-service` 선택을 추가했다. 실제 MCP 샘플 조회와
  개선본의 실제 Ollama 임베딩을 연결한 기능 흐름 비교이며 실제 생성 모델의 품질 비교가 아니다.
- **17장 — 검색 방식:** 동일한 Runbook 정답 질의 4개에서 기존 규칙 어댑터는 **1/4**,
  Ollama 의미 검색은 **4/4**였다. 기존 규칙에는 질문을 합성 모니터링 알림으로 전달했다.
  RAG는 상위 3개 안에 정답 문서가 있는지 평가하며, 원본 전체 서비스의 정확도 측정이 아니다.
- **18장 — 임베딩 공급자:** `qwen3-embedding:0.6b`(1024차원·기준 점수 0.50)와
  `text-embedding-3-small`(1536차원·0.30)을 비교했다. 동일한 고유 검색 질의 12개를
  공급자별 3회 반복했다. 정답 질의 10개의 Hit@3는 **Ollama 30/30, OpenAI 27/30**이고,
  전체 36회 검색 평균은 각각 **36ms, 176ms**였다. 무관 질의 2개의 `no_match`는 양쪽
  모두 6/6회였다. 알려진 소수 합성 질의의 회귀 평가이며 독립적인 신규 평가셋은 아니다.
- 공급자 비교는 같은 문서·질문·검색 범위를 사용하되 공급자별 질의 형식과 기준 점수를
  적용했다. OpenAI 기준 점수는 개발 질의 14개로 선택했다. 색인 생성·준비 질의는 검색
  지연에서 제외했으며 OS 캐시나 모델 로드를 통제한 최초 실행 비교가 아니다.
- 17~19장의 실측 보고서 캡처는 저장된 JSON으로 만든 보고서 화면이다. 서비스 UI나
  LangSmith 제품 화면을 가장한 이미지가 아니다.

이번 표본에서 OpenAI가 더 빠르거나 검색 성공률이 높다는 결과는 없었다. 공급자 교체 가능성과
실제 API 연결을 확인한 결과로 설명한다. 검색 시간은 전체 사용자 대기시간이 아니며,
Ollama 응답의 가상 `usd`를 실제 OpenAI 청구 금액으로 비교하지 않는다.
