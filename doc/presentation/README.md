## 화면과 실측 결과를 읽는 기준

- **10장 전후 화면:** 원본과 6단계 완료본 모두 fake 생성 모델을 사용했다. 실제 MCP
  샘플 조회와 개선본의 실제 Ollama 임베딩을 연결한 기능 흐름 비교다.
- **11~12장 최신 화면:** `1517e8d` 격리본에서 실제 Qwen 생성과 OpenAI 임베딩을
  사용해 합성 문의 한 건을 처리했다. 새로고침 복원·관리자 상세·LangSmith 수집도 확인했다.
  접수 정보는 모델 형식 검사 실패 후 `rules_fallback`으로 보완했다.
- **15장 검색 방식 비교:** 같은 Runbook 정답 질의 4개에서 기존 규칙 어댑터는 1/4,
  Ollama 의미 검색은 4/4였다. RAG는 상위 3개 기준이며 원본 전체 서비스 정확도는 아니다.
- **16장 공급자 비교:** 고유 검색 질의 12개를 공급자별 3회 반복했다. 정답 질의
  10개의 Hit@3는 Ollama 30/30, OpenAI 27/30이며 검색 평균은 각각 36ms, 176ms였다.
  소수 합성 질의의 회귀 평가이며, 전체 사용자 대기시간이나 실제 장애 진단 정확도가 아니다.
- **17장 실측 화면:** 저장된 JSON으로 만든 정적 보고서를 브라우저에서 캡처했다.
  제품 실행 화면과 구분해 표기했다.

최신 브라우저 요청은 약 52.49초였고 LangSmith 하위 실행은 31개였다. 이는 단일 관측값이다.
기존 fake 수집 실험의 하위 실행 35개나 이전 Qwen 통합 확인의 약 47.52초와 섞지 않는다.
현재 샘플 지표와 규칙 검증 통과를 실제 원인 확정·장애 복구 성공으로 표현하지 않는다.
