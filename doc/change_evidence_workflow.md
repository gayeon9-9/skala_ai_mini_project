# 코드 변경과 개선 근거를 함께 남기는 방법

**구현과 테스트는 단계별로, 발표용 비교는 원본과 6단계 완료본을 기준으로 진행한다.**
중간에는 변경 파일·핵심 동작·검증 결과·남은 문제를 간단하게 기록하고, 각 기능마다 전체
비교 촬영과 긴 보고서를 반복하지 않는다. 최종 보고서는 이전 코드·이후 코드·같은 조건의
실행 결과를 연결해 전체 문의 처리 흐름의 개선을 설명한다.

2026-10-21 작업 방식 조정: 이미 확보한 1단계 자료는 보조 근거로 보존한다. 앞으로 중간
캡처는 버그 재현이나 사용자의 요청 등 필요한 경우에만 추가하고, 본 발표의 전후 비교는
6단계 구현·통합 검증이 끝난 뒤 준비한다.

같은 날 사용자가 **각 단계마다 따로 커밋·push하여 나중에 코드를 찾아볼 수 있도록**
요청했다. 단계별 코드·테스트·짧은 변경 기록을 함께 저장하고, 완료 보고에는 GitHub
커밋 링크를 남긴다. 현재 개발 범위와 파일별 설계는 [구현 계획](implementation_plan.md)을 따른다.

현재 1단계 자료:

- [기능 변경 안내](step_01_system_selection.md)
- [코드 읽기와 이전·이후 설명](step_01_code_walkthrough.md)
- [실행 조건·비교 화면·검증 결과](evidence/step_01/README.md)

## 1. 수정 전에 비교 기준을 고정한다

작업을 시작할 때 현재 커밋과 작업 중인 파일을 확인한다.

```bash
git status --short
git rev-parse HEAD
```

기준 커밋, 해결할 문제, 재현 질문, 확인할 결과를 먼저 기록한다. 기존 미커밋 변경이
있으면 그 내용을 별도로 구분하고, 사용자 작업을 덮어쓰거나 기준 코드로 오인하지 않는다.
이전 코드 실행은 임시 복사본에서 진행하며, 현재 작업 폴더를 되돌리는 방법을 쓰지 않는다.

이번 1단계의 코드 비교 기준은 다음과 같다. 문서·증거를 나중에 추가해도 이 기준은 바꾸지 않는다.

| 구분 | 고정 커밋 |
|---|---|
| 이전 코드 | `ee32f7e298517e33aed8d0831a7643eceb756650` |
| 시스템 선택·입력 검증 적용 코드 | `7dd329fdcfce4558fc1d257fbae8286656e45183` |

이미 구현한 기능의 증거를 나중에 만드는 경우에는 **해당 커밋을 다시 실행한 재현 캡처**라고
기록한다. 수정 전에 실제로 촬영해 둔 화면처럼 설명하지 않는다.

## 2. 이전·이후 실행 조건을 맞춘다

두 커밋의 추적 파일을 각각 임시 디렉터리에 준비하고, 별도 포트와 별도 임시 DB로 실행한다.
프로젝트의 `.env`, 기존 `session.db`, 실제 사용자 대화는 복사하지 않는다. 실행 스크립트가
DB를 초기화하는지도 확인하며, 평소 사용하는 서버나 DB를 비교 실험에 사용하지 않는다.

비교 기록에는 다음 조건을 적는다.

| 항목 | 기록할 내용 |
|---|---|
| 코드 | 이전·이후 전체 커밋 해시 |
| 모델 | 같은 `LLM_BACKEND`, 모델 이름, `SUPERVISOR_VERSION` |
| 데이터 | 같은 모니터링·매뉴얼 파일 또는 고정 테스트 응답 |
| 입력 | 질문 원문, 선택 대상, 요청 순서, 새 대화 여부 |
| 실행 | Python·의존성 버전, 포트, 임시 DB 사용 여부, 실행 명령 |
| 화면 | 브라우저 크기, 촬영 단계, 캡처 일시와 시간대 |

검증은 두 갈래로 진행하고, 각 결과에 어느 방식을 사용했는지 적는다.

- **자동 테스트:** `fake` 모델과 고정 MCP 응답으로 분기·조회 대상·검증 규칙을 반복 확인한다.
- **비교 화면:** `fake` LLM과 실제 MCP 도구를 연결해 화면부터 도구 조회까지의 흐름을 확인한다.
  이번 1단계 캡처도 이 방식이다. 실제 MCP의 무작위 변동값과 조회 시각은 그대로 남긴다.

두 방식 모두 `.env` 로딩과 외부 추적을 끄고 실제 API 키를 실험 프로세스에 전달하지 않는다.
현재 프로젝트에서 사용하는 설정은 다음과 같다. 이 설정 자체가 포트나 DB를 분리하지는
않으므로, 별도 임시 소스와 실행 도구의 포트 설정도 함께 확인한다.

```text
PYTHON_DOTENV_DISABLED=1
LANGSMITH_TRACING=false
LANGCHAIN_TRACING_V2=false
LLM_BACKEND=fake
SUPERVISOR_VERSION=v2
```

`fake` LLM을 쓴다고 전체 실행이 고정되는 것은 아니다. 기존 MCP 도구는 CPU·메모리에
무작위 변동값을 더하고 현재 시각도 반환한다. 정확한 수치 비교에는 고정 응답이 필요하다.
실제 MCP 도구를 사용한 캡처라면 변동값을 그대로 남기고, 수치가 같다는 주장을 하지 않는다.
LLM·MCP를 대체한 테스트는 어떤 부분을 대체했는지 명시한다.

기존 화면에 없던 선택창은 이전 실행에 임의로 추가하지 않는다. 동일한 증상 질문을 넣고,
이후 화면에서만 선택 대상을 지정했다면 그 차이를 입력 조건에 적는다. 이 비교는 새 접수
방식의 효과를 보여주며, 완전히 같은 API 요청의 성능 비교는 아니다. 기존 API 호환성은
선택값을 생략한 별도 사례로 확인한다.

## 3. 원본 화면과 응답을 함께 보관한다

최종 비교 자료는 `doc/evidence/final/`에 원본 캡처와 결과 파일, 설명용 `README.md`를 둔다.
기존 `doc/evidence/step_01/` 자료는 그대로 유지한다. 중간 변경에서는 간단한 변경·검증
기록을 기본으로 하고, 화면 증거가 필요할 때만 해당 단계의 폴더에 추가한다.
최종 사례의 이전·이후 이미지 파일명을 표로 연결하고, HTTP 상태·응답·SSE 이벤트와
도구 호출 목록을 함께 남긴다. 자동 재현 스크립트가 있으면 실행 방법도 기록한다.

- 전송 전의 선택 상태와 전송 후의 완료 상태처럼, 촬영 시점을 맞춘다.
- 원본 캡처의 글자·답변·오류를 수정하거나 지우지 않는다. 실패 화면도 그대로 보관한다.
- 설명용 나란히 보기나 확대 이미지는 별도로 만들고, 원본을 가리키는 링크를 둔다.
- 결과 파일에는 키·토큰·실제 사용자 대화를 넣지 않는다. 민감한 입력은 처음부터 실험에 쓰지 않는다.
- 화면만으로 확인할 수 없는 도구 호출 수나 저장 결과는 응답·로그·DB 검증으로 보완한다.

## 4. 코드와 측정 결과를 연결한다

코드 설명에는 **파일명, 함수명, 고정 커밋**을 적고 해당 버전의 실제 코드를 짧게 발췌한다.
현재 파일의 행 번호만 적으면 다음 변경에서 위치가 바뀔 수 있다. GitHub 링크도 브랜치
이름보다 커밋 해시를 사용한다. 아래처럼 해당 버전의 원문을 확인할 수 있다.

```bash
git show ee32f7e298517e33aed8d0831a7643eceb756650:agent/graph.py
git show 7dd329fdcfce4558fc1d257fbae8286656e45183:agent/graph.py
```

각 변경은 “기존 코드가 한 일 → 문제를 재현한 입력 → 바꾼 코드 → 관찰한 결과”로 설명한다.
의미를 요약한 의사 코드는 실제 코드 발췌와 구분한다.

결과 표에서는 **기대 결과**와 **실제로 관찰한 값**을 분리한다. 예를 들어 “선택 대상 하나만
조회해야 함”은 기준이고, 실행에서 얻은 대상 목록과 호출 횟수가 측정 결과다. 전체 사례 중
통과한 수, HTTP 상태, 조회 대상, 모델 호출 여부처럼 직접 확인한 항목을 적는다.
현재 1단계의 실제 수치와 화면은 [증거 문서](evidence/step_01/README.md)를 기준으로 삼는다.

테스트 실행 시간이나 한 번의 브라우저 응답 시간을 서비스 속도 개선률로 바꾸지 않는다.
특히 fake 모델·고정 지연·재시도·무작위 지표가 섞인 실행으로 실제 LLM의 속도나 비용을
개선했다고 주장하지 않는다. 성능을 평가하려면 별도 실험에서 반복 횟수와 측정 구간을 정한다.

## 5. 한계까지 적고 변경 단위로 저장한다

성공 사례 외에 미지원 입력, 실패 사례, 기존에 남아 있는 문제를 적는다. 샘플 데이터로
동작을 확인한 결과와 실제 운영 원인 규명은 구분한다. 자동 테스트 통과가 답변의 사실성이나
실제 운영 서버 연동까지 검증했다는 뜻은 아니다.

작은 기능 단위로 코드를 수정하고 검증한 뒤, 간단한 변경 요약을 남긴다. 최종 통합 검증 후
아래 7개 항목의 보고서와 비교 화면을 완성한다. 기능 코드와
후속 증거 문서가 별도 커밋이면 두 커밋의 역할을 적는다. 검증과 설명을 마친 단위로 커밋하고,
사용자가 요청한 저장소에 푸시한다. 커밋할 때 `.env`, DB, 캐시, 로그가 포함되지 않았는지
확인한다. 이후 변경에서도 같은 방식으로 비교 자료를 이어서 남긴다.

커밋 제목에는 단계와 목적을 넣는다. 예: `feat(step-02): preserve sessions and inquiry state`.
한 단계가 크면 동작 보존 리팩터링과 기능 추가를 각각 커밋하되, 모두 같은 단계 번호를 쓴다.
검증이 끝난 작업 단위를 push하고, 단계 완료 기록에는 시작 커밋·완료 커밋·테스트 명령과
결과를 남긴다. 이전 단계를 지우는 squash·amend·force-push는 이 기록 방식에 사용하지 않는다.

현재 커밋의 번호를 같은 커밋의 문서 안에 미리 적을 수는 없으므로, 변경 기록 파일을
해당 코드와 함께 커밋하고 완료 후 사용자에게 확정된 링크를 전달한다. 필요하면 다음
기록 갱신 때 이전 단계의 링크를 추가한다. 문서에 번호를 넣기 위해 커밋을 반복 수정하지 않는다.

```bash
# 단계별 변경 이력을 확인한다.
git log --oneline --all
# 작업 폴더를 되돌리지 않고 특정 시점의 파일을 읽는다.
git show 7dd329f:agent/graph.py
```
