# OpenAI 임베딩 전환: 실제 실행·검색 비교 결과

측정일: 2026-10-21. **OpenAI 임베딩과 로컬 Qwen 답변 생성의 연결은 실제로 동작했다.
다만 이번 표본에서는 검색 속도나 정답 문서 발견률이 개선되지 않았다.**
이 자료는 같은 문서·질문에서 임베딩 공급자를 비교한 결과이며,
원본 서비스와 전체 개선본의 비교는 [기존 최종 자료](../final/README.md)에서 구분해 본다.

## 1. 무엇을 바꾸고, 어떻게 비교했나

| 항목 | 기존 로컬 임베딩 | 전환한 API 임베딩 |
|---|---|---|
| 검색 모델 | Ollama `qwen3-embedding:0.6b` | OpenAI `text-embedding-3-small` |
| 벡터 차원 | 1,024 | 1,536 |
| 검색 문턱값 | 기존 0.50 유지 | dev에서 선택한 0.30 고정 |
| 검색 질의 | Qwen용 지시문 + 질문 | 질문 원문 |
| 검색 범위 | 동일한 문서 10개·시스템·사용자/운영자 구분·상위 3개 | 동일 |
| 답변 생성 | 이 비교에서는 생성하지 않음 | 별도 통합 확인에서 Qwen 유지 |

최종 회귀 비교는 **고유 검색 질의 12개 × 3회 = 공급자별 36회**다.
정답 문서가 있는 질의 10개와 근거가 없는 질의 2개로 구성되며,
기존에 확인했던 test 사례를 사용했다. 새로 보지 않은 독립 평가셋이라는 의미는 아니다.
색인 생성과 준비용 질의는 검색 지연 측정에서 제외했고, 동시성 1로 공급자 실행 순서를
교대했다. 모델을 내리거나 OS 캐시를 통제한 최초 실행 속도 비교는 아니다.
[실행 조건·원시 결과](test.json)

## 2. 최종 검색 결과

| 지표 | Ollama | OpenAI API |
|---|---:|---:|
| Hit@1: 첫 번째 결과에 정답 문서 포함 | 90% · 27/30회 | 90% · 27/30회 |
| Hit@3: 상위 3개에 정답 문서 포함 | 100% · 30/30회 | 90% · 27/30회 |
| Recall@3 | 100% | 90% |
| 근거 없는 질의의 `no_match` 처리 | 100% · 6/6회 | 100% · 6/6회 |
| 검색 지연 평균 | 0.036초 | 0.176초 |
| 검색 지연 중앙값 | 0.033초 | 0.175초 |
| 검색 지연 p95 | 0.060초 | 0.220초 |
| API/검색 오류 | 0건 | 0건 |
| 다른 시스템·독자 범위 문서 반환 | 0건 | 0건 |

정답 지표의 분모 30회는 정답 있는 고유 질의 10개를 3회 반복한 수이며,
서로 다른 질문 30개를 뜻하지 않는다. 이번 최종 질의들은 정답 문서가 하나씩이므로
Hit@3와 Recall@3가 같다. 평균 검색 시간은 API 쪽이 **약 140ms 더 길었다**.
이 시간은 문서 검색 단계만의 측정값으로, 사용자 전체 대기시간이나 생성 모델 속도가 아니다.
[지표 분모·지연 통계](test.json)

자료 종류별 Hit@3를 고유 질의로 보면 다음과 같다. 각 질의의 판정은 3회 모두 같았다.

| 정답 문서가 있는 질의 | Ollama | OpenAI API |
|---|---:|---:|
| 사용자 FAQ 6개 | 6/6 | 6/6 |
| 운영자 Runbook 4개 | 4/4 | 3/4 |

따라서 발표에서는 “FAQ 검색은 같은 결과를 유지했지만, 운영자 문서 한 질의를 놓쳤다”고
설명할 수 있다. 이 작은 합성 표본의 비율을 일반적인 장애 진단 정확도로 확대하지 않는다.

## 3. 놓친 질의와 문턱값 선택

실패 사례는 `gateway-service`의 운영자 질의
**“서비스 사이 패킷 손실과 upstream 호출 대기 제한 초과”**다.
정답은 `runbook:network-timeout`이며, OpenAI 검색은 문턱값 0.30에서 3회 모두
빈 결과인 `no_match`를 반환했다. API 통신 오류나 실제 네트워크 장애를 재현한 결과가
아니라, 정답 문서를 찾지 못한 검색 사례다. 보고서에는 문턱값에서 제외된 후보의
원점수가 없으므로, 어느 문서가 몇 점 차이로 제외됐는지까지 확정할 수 없다.
[실패 원시 행: test-03, check_index 1](test.json)

OpenAI 문턱값 0.30은 dev의 고유 검색 질의 14개에서 선택했다.
Hit@3와 근거 없음 처리율의 평균을 우선하고, 동점이면 정답 집합 밖 문서 수와
Precision@3 등을 비교하는 규칙을 사용했다. **0.30 곡선 지점에서는 정답 12/12,
근거 없음 2/2를 처리했지만**, 최종 회귀 질의에서는 위 한 사례를 놓쳤다.
`dev.json`의 최상위 `summaries`는 초기 문턱값 **0.50** 결과다.
선택된 0.30 결과는 `calibration.curve`에서 `min_score=0.30`인 항목을 읽어야 한다.
[문턱값 선택 근거](dev.json)

후속 개선은 이 실패를 별도 회귀 사례로 남기고, 네트워크 증상의 다른 표현을
개발용 자료에 추가하는 방향이다. test 결과만 보고 문턱값을 낮춘 뒤 같은 test를
독립 검증 결과로 제시하지 않는다.

## 4. 실제 API 연결과 Qwen 통합 확인

| 확인 항목 | 실제 결과 | 근거 |
|---|---|---|
| OpenAI 합성 문장 연결 확인 | 성공 · 1회 · 입력 5토큰 · 1,536차원 | [probe.json](probe.json) |
| 문의 정보 정리 모델 | 로컬 `qwen3:0.6b` | [hybrid_model.json](hybrid_model.json) |
| 답변 작성 모델 | 로컬 `qwen3:8b` | [hybrid_model.json](hybrid_model.json) |
| 문서 검색 | OpenAI small · 문턱값 0.30 · 로그인/브라우저/접속 FAQ 반환 | [hybrid_model.json](hybrid_model.json) |
| 문의 처리 | 완료 · 검증용 호출 관측 시간 47.519505초 | [hybrid_model.json](hybrid_model.json) |
| 답변 규칙 검증 | 첫 시도 통과 · 출처 3개 | [hybrid_model.json](hybrid_model.json) |
| 접수 정보 추출 | 모델 형식 검증 실패 후 `rules_fallback` 적용 | [hybrid_model.json](hybrid_model.json) |

합성 문의는 “오전 9시부터 로그인 후 화면이 넘어가지 않아요. 오류 메시지는 없어요.
윈도우 크롬을 사용해요.”였다. 증상·시각·명시적 오류 없음·사용 환경을 보존했지만,
접수 정보는 모델이 바로 올바르게 추출한 결과가 아니라 **규칙 기반 보완 경로**로 정리됐다.

47.519505초는 `graph_wall_seconds`로 기록된 검증용 서비스 호출 시간이며,
브라우저 HTTP 전송 시간을 포함한 사용자 체감 시간이 아니다.
규칙 검증 통과는 출처·수치 등 구현한 검사 조건을 통과했다는 뜻이며,
의미상 모든 안내가 옳거나 실제 장애 원인을 진단했다는 증거는 아니다.
한 건의 통합 성공을 생성 품질 개선률로 제시하지 않는다.

## 6. 재현 기준과 발표 결론

- [후속 검증 기록](api_verification.json): 기본 점수 반영 후 자동 테스트 **189개 + 하위 검사 111개**,
  원시 자료·코드·점수·실행 결과의 정합성 검사 **13개**가 모두 통과했다.
- 실측 기준 코드는 `3bdc39cd88d4fec97f957fa72bf4198895e36048`이다.
  dev/test의 문서·사례·검색 코드 지문은 일치하며, test에 기록된 dev 보고서 해시도
  실제 `dev.json`과 일치한다. test의 `git_dirty=true`는 실험 산출물이 추가된 상태이고,
  저장된 비교 대상 검색 소스의 해시는 dev와 같다.
- [verification.json](verification.json)은 **이전 권한 거절 시점**의 구현 검증 기록이다.
  당시 `not_run`을 현재 실측 상태로 읽지 않는다. 이후 사용자가 실제 검증을 허용한
  결과가 이 보고서의 probe/dev/test/hybrid 자료다.
- 공급자 교체로 로컬 임베딩 모델의 실행·관리 부담을 줄일 가능성은 있다.
  그러나 이번에는 메모리·CPU·전력·동시 처리량을 측정하지 않았으므로 기대 효과로 구분한다.
- **채택 설명:** “답변 생성은 Qwen으로 유지하면서 임베딩을 외부 API로 교체할 수 있는
  구조를 구현하고 실제 연결을 확인했다. 같은 질문의 비교에서 FAQ 검색 결과는 유지했지만,
  전체 Hit@3는 100%→90%, 평균 검색 시간은 36ms→176ms였다. 외부 API 활용 요구는
  충족하되, 더 빠르거나 더 정확해졌다고 주장하지 않는다.”
