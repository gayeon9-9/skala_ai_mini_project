# 최종 시연 후 접수·답변 검증 보완

- 수정 전 기준: `adce28f0b2b28a38549e471a102a567dcf3a4f36` (앱 코드는 최종 시연의 `1517e8d`와 동일).
- 고정 입력: `오전 9시부터 로그인 후 화면이 넘어가지 않아요. 오류 메시지는 없어요. 윈도우 크롬을 사용해요.`
- 선택 대상: `auth-service`.
- 모델 조건: 접수 `qwen3:0.6b`, 답변 `qwen3:8b`, 임베딩 OpenAI `text-embedding-3-small`, 검색 임계값 0.30.
- 기존 결과: [최종 시연 원본](../final_openai/README.md). 네 필드 형식 검증 실패 후 규칙 추출로 대체됐으며, 오류 메시지가 없다는 문의에 504 문서 안내가 포함됐다.
- 기존 원시 모델 추출 출력은 남아 있지 않으므로 정확한 잘못된 필드 조합은 확정하지 않는다. 상태별 JSON Schema와 실제 접수 검증 사이의 허용 범위 차이를 보완한다.

이번 수정의 코드·검증 결과는 이 폴더에 별도로 기록한다. 기존 PPT, 화면 캡처, 검색 성능 측정은 당시 버전의 결과로 보존한다.

## 문제와 반영 내용

| 문제 | 코드 변경 | 사용자·관리자 효과 |
|---|---|---|
| 생성 스키마가 `provided + value:null` 등 실제 검증에서 거부할 조합도 허용 | `agent/intake_llm.py`의 상태별 JSON Schema 분기와 정확한 객체 형식 예시 | 모델에 요구하는 형식과 저장 전 검증 계약을 맞춘다. 원문 검증·규칙 대체 경로는 유지한다. |
| 문서에 나온 오류 예시를 사용자에게 표시된 오류와 구분하지 않음 | 작성 문맥에 검증된 누적 접수 필드와 허용 HTTP 코드 목록 전달 | 오류 메시지 없음·모름·미언급을 존중한 안내를 요구한다. |
| 문서 ID가 유효하면 무관한 504 안내도 검증 통과 | `agent/answer_grounding.py` 추가, 검증에 `intake` 전달 | 실제 접수한 오류 메시지에 없는 HTTP 4xx/5xx 코드를 반려하고 기존 최대 3회 작성·검증 흐름을 사용한다. |
| 지시·검증만 추가해도 모델이 문서의 504를 반복 언급 | 미확인 HTTP 코드가 제목·본문에 있는 문서 전체를 작성 근거에서 제외 | 프롬프트·검증·fake 작성기·제한 안내에 같은 필터를 적용한다. 원본 검색 결과와 관리자 근거는 보존한다. |
| 작성에 적용할 문서가 전부 제외돼도 불필요한 모델 호출 가능 | `agent/graph.py`에서 답변 생성 LLM 대신 고정된 제한 안내를 만들고 검증 | 검색 성공과 현재 문의에 적용할 문서 부족을 구분하고, 제외된 문서의 조치를 추측하지 않는다. |
| 모델이 내부 JSON 항목명을 문서 출처처럼 표시 | `clean_internal_annotations()`로 정해진 내부 항목명만 검증 전에 제거 | 사용자용 문장·실제 문서 ID·HTTP 코드는 그대로 두어 이후 검증을 피하지 않게 한다. |
| 현재 기능과 오래된 실습 설명이 섞인 문서 진입점 | 루트 `README.md` 신설, `doc/README.md` 갱신 | 실행 구성·파일 역할·현재 한계·단계별 증거를 한곳에서 찾는다. |

접수 정보는 작성 함수에 전달할 복사본에만 추가한다. 기존 검색 결과나 관리자 저장 근거를 바꾸지 않으며, 원본 문서 파일·임베딩·유사도 임계값도 이번 수정에서 변경하지 않는다. 답변에서 제외한 문서는 사용자 답변의 인용 근거로도 허용하지 않지만, 관리자는 저장된 원본 검색 결과에서 확인할 수 있다.

## 핵심 코드 전후

기존 생성 스키마는 상태와 값의 자료형을 따로 허용했다.

```python
"status": {"enum": ["unmentioned", "none", "unknown", "provided"]},
"value": {"type": ["string", "null"]},
```

이제 `provided`는 비어 있지 않은 값·근거, `none/unknown`은 null 값과 비어 있지 않은 근거, `unmentioned`는 null 값·null 근거를 요구한다. JSON 형식이 맞아도 원문에 없는 정보는 기존 검증기가 계속 거부한다.

기존 답변 검사는 검색·관측 근거만 받았다. 이제 검증된 접수 정보도 받는다.

```python
checked = validate_answer(
    draft, state["selected_system"],
    state.get("collected", []), state.get("retrieval", {}),
    intake=state.get("intake", {}),
)
```

허용 코드의 근거는 `error_message.status == "provided"`인 원문 값이다. 증상의 `504는 안 떠요`나 샘플 알림의 `504`는 사용자 오류를 확인한 근거로 사용하지 않는다. 사용자가 실제 `504 Gateway Timeout`을 보고하면 그 코드는 안내할 수 있다.

작성에 사용하는 문서 선택은 같은 규칙을 재사용한다.

```python
return [doc for doc in documents if not unsupported_http_error_codes(
    doc.get("title", "") + "\n" + doc.get("text", ""), intake)]
```

예를 들어 오류 메시지가 없는 문의에서 504가 든 `faq:connectivity`가 검색돼도 작성 문맥에서 제외한다. 남은 `faq:login`, `faq:browser`는 사용할 수 있으며, 검색 원본의 `faq:connectivity`는 삭제하지 않는다.

`hybrid_model.json`은 내부 표기 정리를 추가하기 전의 원본이다. 해당 응답에는 `[sample_monitoring]`, `[confirmed_http_error_codes]` 같은 내부 항목명이 남았다. 이후 코드는 정해진 내부 항목명을 검증 전에 제거하도록 보완했다. [저장 응답 재생](rendering_replay.json)에서 내부 표기 제거·실제 인용 보존·미확인 504 없음·그 외 내용 보존을 확인했다. 새 모델/API 호출이나 UI 캡처 결과가 아니다.

## 자동 검사와 보존 자료

- [최종 자동 검사](tests.json): 217개 테스트·173개 하위 검사 통과. 기존 189개에서 새 회귀 테스트 28개를 추가했으며, 접수 계약·문서 적용·답변 검사·표시 보완과 기존 기능의 회귀를 확인했다. 실제 모델 정확도 측정은 아니다. 검사 대상은 [최종 소스 해시](source_sha256.json)와 함께 보존한다.
- [1차 자동 검사](initial_tests.json): 211개 테스트·170개 하위 검사 통과, 실패·오류·건너뜀 0. 새 회귀 테스트 22개를 추가한 접수·답변 검사 버전의 결과이며, 이후 문서 적용 필터·표시 보완까지 포함한 최종 결과와 구분한다.
- [1차 저장 답변 회귀](initial_saved_answer_regression.json): 당시 통과한 504 안내를 새 코드 검사로 반려했고, 제한 안내에서는 제목의 코드를 가린 결과다. 이 중간 동작과 [1차 소스 해시](initial_source_sha256.json)를 보존한다.
- [문서 필터를 적용한 저장 답변 회귀](saved_answer_regression.json): 최종 시연에 저장된 동일 답변·관측·문서·접수를 모델/API 호출 없이 검사했다. 미확인 504와 제외된 문서의 인용을 반려하며, 작성·제한 안내에는 적용 가능한 문서만 남는다. 원본 검색 결과 보존 등 6개 확인 항목을 통과했다.
- [접수 연결 제한 기록](intake_sandbox_attempt.json)과 [전체 흐름 연결 제한 기록](hybrid_sandbox_attempt.json)은 실행 환경의 네트워크 제한으로 `ConnectError`가 난 첫 시도다. 모델의 추출·생성 실패와 구분해 보존했다.

## 해석할 때 남겨야 할 한계

- 접수 전후 실험은 한 건의 계약 호환성 확인이다. 새 실행에서 실패 원인이 재현됐다는 뜻이며, 최종 시연 당시 저장하지 않은 원시 출력까지 확인했다는 뜻은 아니다.
- HTTP 코드 검사는 제한된 형식 규칙이다. 일반 자연어의 인과관계, 코드가 없는 무관한 안내, 모든 숫자 문맥을 완벽하게 판별하지 않는다. 검사 통과가 답변 전체의 의미·원인 정확도를 보장하지 않는다.
- 문서 전체를 제외하므로 같은 문서 안의 유용한 일반 안내도 빠질 수 있다. 적용 조건별로 문서를 분할하면 이를 더 세밀하게 선택할 수 있다. 현재는 접수와 맞지 않는 코드를 모델 문맥에 넣지 않는 보수적인 방식을 사용한다.
- 프롬프트·검증·fake 작성기·제한 안내는 같은 문서 적용 규칙을 사용한다. `fake` 결과와 자동 테스트는 실제 LLM 생성 품질 개선으로 집계하지 않는다.
- 이번 수정은 검색기의 정확도·속도 개선이 아니다. 과거 임베딩 비교 수치와 UI 지연시간을 새로운 코드의 성능으로 재사용하지 않는다. 기존 PPT와 `adce28f`의 UI 증거는 그대로 보존한다.
