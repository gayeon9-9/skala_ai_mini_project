# 2단계 — 대화와 문의 접수 기록 보존

시작 커밋: `9330a80`. 1단계 선택·검증 재검토에서 별도 필수 수정은 발견하지 않았다.
이번 단계는 저장 수명과 복원 기능을 개선하며, RAG·자연어 정보 추출은 후속 단계다.

| 기존 문제 | 개선 | 사용자·관리자 효과 |
|---|---|---|
| 실행 스크립트가 `session.db`를 삭제 | 자동 삭제 제거, 기존 messages 테이블을 유지하고 접수 테이블 추가 | 재시작해도 대화·문의 내역 보존 |
| 새로고침마다 새 thread | 브라우저 식별자 보존 + 서버 조회 복원 + 새 문의 버튼 | 같은 문의를 이어서 대화하거나 명시적으로 새 문의 시작 |
| 전송 실패 후 같은 문의를 다시 처리할 수 있음 | request_id로 중복 방지, 처리 중 요청 충돌 검사, 완료 결과 재사용 | 재시도할 때 중복 접수·중복 도구 조회 방지 |
| 처리 성공 후에만 질문 저장, SSE 완료를 저장 전에 표시 | 질문을 먼저 저장, 최종 답변·결과·상태를 한 트랜잭션으로 저장한 후 완료 전송 | 실패한 문의도 원문·상태 확인. 저장되지 않은 결과를 완료로 안내하지 않음 |
| 같은 대화에서 대상이 뒤섞일 수 있음 | 서버에서 대상 불변, 화면에서 대상 변경 시 새 문의 | 다른 시스템의 대화·점검 결과 혼합 방지 |

## 변경 파일

- `agent/session_store.py`: SQLite 연결·잠금·트랜잭션 공유. `SESSION_DB_PATH`로 별도 시연 DB 지정 가능.
- `agent/inquiry_store.py`, `inquiry_models.py`: 접수 ID, 원문, 상태, 요청 중복 방지, 결과·상세 조회.
- `agent/chat_service.py`: POST/SSE 공통 접수·실행·저장. 요청 추적을 공통 서비스로 이동.
- `server.py`, `agent/deps.py`: 저장소 주입, 대화 복원 API, HTTP/SSE 오류와 충돌 응답.
- `web_chat.html`, `web_demo_server.py`: 복원·새 문의·재시도 UI 및 프록시. 프록시 기본 바인딩은 로컬 전용.
- `sh/run_agent_openai.sh`, `sh/run_agent_ollma.sh`: DB 자동 삭제 제거.
- `requirements-dev.txt`, `pytest.ini`, `tests/`: 기존 unittest를 유지하고 pytest로 함께 실행.
- `evals/cases.json`: 합성 평가 20개 초안(dev 10/test 10). 아직 품질 측정 결과가 아니다.

## 핵심 처리 순서

`입력 검증 → 대상/요청 충돌 확인 → 원문 저장 → AI 처리 → 결과·답변 원자 저장 → 완료 응답`.
같은 완료 요청을 재전송하면 저장한 결과를 반환한다. 실패·중단된 최신 요청은 같은 ID로
재시도하되 원문을 중복 저장하지 않는다. 후속 대화가 진행된 과거 실패 요청의 재실행은
문맥 역전을 막기 위해 거부한다. 저장 실패 시 완료 답변을 전송하지 않는다.

`completed`는 **답변 저장 완료**이며 실제 장애 해결을 뜻하지 않는다. 문의 처리 상태와
운영 장애 상태는 서로 다르다. 브라우저 캐시는 복원 실패 때 화면을 보존하는 보조 수단이고,
성공한 접수의 원본은 서버 DB다. 화면 복원 API는 전체 프롬프트·그래프 결과를 반환하지 않는다.

## 검증

`.venv/bin/python -m pytest -q` — 43개 통과(기존 17개 포함), 38 subtests 통과.
임시 SQLite, fake LLM, MCP 대역을 사용해 저장·복원·재시도·충돌·실패·원자 롤백을 확인했다.
화면 상태 검사는 실제 HTML의 Vue setup 코드를 Node VM에서 실행한다(브라우저 화면 촬영 아님).
SSE 최종 이벤트를 받은 순간 저장소가 완료인지 확인하는 테스트도 포함한다.

최종 원본/완성본 화면 비교는 6단계 통합 후 진행한다. 현재 자동 테스트가 실제 LLM의
답변 품질 또는 장애 진단 정확도를 입증하지는 않는다.

## 남은 범위

- 재시작 복구는 단일 서버 워커 기준. 다중 워커에서는 작업 소유권·lease가 필요하다.
- thread ID는 인증이 아니다. 사용자/관리자 인증은 사내 배포 전 추가해야 한다.
- 문의 내용은 아직 원문이며 3단계에서 구조화한다. 관리자 화면은 6단계에서 추가한다.
- 검증 전 초안은 별도 표시되지만 제거되지 않았다. 4~5단계에서 최종 검증 표시를 완성한다.
