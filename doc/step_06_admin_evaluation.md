# 6단계 — 관리자 조회·실행 추적·최종 평가

시작 커밋: `9799f23`. 관리자 화면은 `http://localhost:8600/admin`에서 연다.
현재는 인증 없는 로컬 실습용이며, 실제 사내 배포에는 사용자·관리자 권한 구분이 필요하다.

| 기존 문제 | 반영 내용 | 사용자·관리자 효과 |
|---|---|---|
| 최종 채팅만으로 접수 현황 파악이 어려움 | 목록·상태 필터·페이지 이동·상세 조회 | 관리자가 여러 문의를 확인하고 원문을 찾아볼 수 있음 |
| 점검·문서·추가 확인 사항이 흩어짐 | 같은 접수의 필드·샘플 관측·FAQ·Runbook·검증 결과 표시 | 다시 질문할 항목과 확인할 근거를 함께 볼 수 있음 |
| 이전 완료 답변과 새 요청 실패 혼동 가능 | 근거를 만든 요청 ID·시각·최신 여부 표시 | 과거 관측을 현재 상태로 오인하는 문제 완화 |
| 실행 기록에 프로젝트 버전·검색 근거 연결이 부족 | POST/SSE 공통 요청 추적에 모델·코드·문서·접수·검증 메타데이터 추가 | 잘못된 결과가 어느 버전·단계에서 생겼는지 추적 가능 |
| 평가를 눈으로만 비교 | 고정 dev/test 검색 평가 CLI·HTTP 흐름 검사 도구 | 분모·환경·원시 응답을 보존해 발표 수치를 다시 확인 가능 |

## 핵심 파일

- `agent/inquiry_summary.py`: 저장된 결과로 관리자 응답을 구성한다. LLM 요약을 다시 생성하지 않는다.
- `server.py`: `GET /admin/inquiries`, `GET /admin/inquiries/{id}`. 목록 크기·상태 검증 및 404 처리.
- `web_admin.html`, `web_demo_server.py`: 관리자 화면과 동일 출처 프록시.
- `agent/observability.py`, `chat_service.py`, `deps.py`: 요청별 실행 추적·버전·소요 시간 연결.
- `evals/evaluate.py`: 실제 로컬 임베딩 검색과 기존 Runbook 규칙 어댑터 비교.
- `tools/verify_langsmith.py`: 합성 문의 한 건을 실제 수집하고 저장된 run·하위 실행·평가 피드백 확인.
- `tools/verify_local_model.py`: 기본 로컬 생성 모델의 실제 실행을 임시 DB로 확인하고 실패도 기록.
- `tools/check_final_flow.py`, `compare_versions.py`: 별도 커밋·포트·DB에서 원본/완료본 HTTP 확인.

관리자 `completed`는 **답변 저장 완료**이며 장애 복구 완료를 뜻하지 않는다.
운영자 매뉴얼은 참고 근거로만 보여준다. 서버 재시작이나 복구 명령을 실행하지 않는다.

## 추적과 평가를 다시 실행하는 방법

```bash
.venv/bin/python -m pytest -q
.venv/bin/python evals/evaluate.py --split dev --output /tmp/rag-dev.json --repetitions 1
.venv/bin/python evals/evaluate.py --split test --output /tmp/rag-test.json --repetitions 1
.venv/bin/python tools/verify_langsmith.py --output /tmp/langsmith-check.json
.venv/bin/python tools/verify_local_model.py --output /tmp/local-model-check.json
```

검색 평가는 Ollama와 `qwen3-embedding:0.6b`가 필요하다. LangSmith 검사는 유효한
키·연결이 필요하며 합성 문의만 전송한다. 일반 자동 테스트는 외부 전송을 끈다.
키·실제 문의 DB·모델 파일·벡터 캐시는 커밋하지 않는다.

추적의 노드별 시간과 `processing_seconds`를 구분한다. 후자는 그래프 실행 시작부터
DB 저장 직전까지이며 HTTP 전송·화면 렌더링까지 포함한 시간은 아니다. 재전송 시에는
이전 저장 결과와 원래 실행 run ID를 돌려주므로 새 추론 시간처럼 해석하지 않는다.

FAQ는 새로 추가한 기능이어서 원본과의 정확도 증가율을 계산하지 않는다. 기존 Runbook
6개에 대해서만 같은 검색문을 기존 규칙과 임베딩 검색에 넣는다. 원래 규칙의 입력인
모니터링 알림에 검색문을 넣은 비교용 어댑터이므로 원본 서비스 전체 성능과 구분한다.

최종 확인용 test 질문은 설정을 고정한 뒤 실행한다. 검색 점수는 장애 원인 확률이 아니며,
상위 3개에 정답이 있다는 사실만으로 나머지 후보도 관련 있다고 해석하지 않는다.

## 검증 기록

기능 코드 기준 전체 **133개 테스트·73개 하위 사례 통과**. 관리자 API·프록시·화면 상태,
페이지 분할, 이전 근거 표시, 추적 SDK 실패 격리, 평가 집계의 분모를 포함해 확인했다.

최초 외부 수집 확인에서는 요청 1개와 하위 실행 38개·메타데이터 수집에 성공했으나,
FAQ의 정상 문장인 “화면 문제가 해결되었다는 뜻은 아닙니다”가 복구 완료 주장으로
오차단됐다. 최초 결과를 `langsmith_initial.json`에 보존하고, 직접 연결된 부정 표현만
구분하도록 보완했다. 실제 FAQ 4개 각각 및 3개 동시 검색 문맥으로 회귀 테스트를 추가했다.
검색 코드·문턱값·최종 확인용 정답은 바꾸지 않았다.
보완 후 전체 **135개 테스트·81개 하위 사례 통과**.

실제 기본 생성 모델 확인에서는 128.96초 뒤 제한된 안내로 끝났다. 처음에는 92%를
근거 없는 비율로 판정했으나 실제 샘플의 `connection pool 92% used` 알림에 있는 수치였다.
이 결과를 `local_model_initial.json`으로 보존하고 선택한 대상의 알림 수치도 검사 근거에
포함했다. 같은 92%를 CPU 수치로 바꿔 쓰거나 다른 대상의 알림 수치를 쓰는 경우는 계속 차단한다.
형식 검사 실패도 있었으므로 이 최초 실행을 모델의 사실 오류 탐지 성공 사례로 사용하지 않는다.
알림 수치 보완 후 전체 **136개 테스트·81개 하위 사례 통과**.

재확인 결과 `1.`로 시작하는 일반 Markdown 목록이 `1)` 전용 형식 검사에 반려됐다.
반려 초안을 `local_model_numbering.json`에 그대로 보존하고 두 표기를 허용했다.
번호 스타일을 바꾸어도 잘못된 수치·가짜 인용이 차단되는 회귀 테스트를 추가했다.
대상·수치·인용 검사를 유지하면서 정상적인 번호 표기를 인정한 수정이다.
전체 **137개 테스트·81개 하위 사례 통과**.

기능 코드의 단위·통합 검사와 실제 외부 수집/브라우저 비교 증거를 나누어 기록한다.
실행 결과·원시 응답·실제 캡처는 [최종 비교 자료](evidence/final/README.md)에 보존한다.

## 남은 범위

현재 시스템 점검은 샘플 데이터다. 실제 오류 로그, 배포 이력, 사용자 환경 수집은
연동하지 않았다. 작은 로컬 모델은 접수 추출을 실패할 수 있어 원문 기반 규칙으로
전환하고 이를 표시한다. 규칙 검증은 모든 의미 오류를 판정하지 못한다.
목록 API는 소규모 실습 DB에 맞춘 구조이며 대규모 조회·다중 프로세스 운영은 별도 확장이 필요하다.
