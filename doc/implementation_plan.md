## 1. 보내준 계획에서 유지할 것과 조정할 것

핵심 조합은 **RAG + 모듈화 + 자동 테스트 + LangSmith**로 한다. 기존 LangGraph와 MCP를
유지하고, Multi-Agent·Hybrid 검색·자동 복구는 이번 최소 구현 범위에서 제외한다.

| 항목 | 현재 코드에서 확인한 사실 | 진행 방식 |
|---|---|---|
| 모듈화·DI | `agent/deps.py`의 `SupervisorDeps`와 `graph.py`의 노드 주입이 있음 | 새 검색기·접수 저장소를 기존 DI에 추가하고, 기능을 변경할 때 책임별로 분리 |
| 저장 | `session_store.py`가 SQLite에 메시지를 저장함 | 실행 스크립트의 DB 삭제와 화면의 새 thread 발급 문제를 고치고 접수 상태 추가 |
| 자동 테스트 | `unittest` 기반 17개, 일부는 API·그래프·프록시 통합 검사 | 기존 검사를 보존하고 신규 기능에 단위 테스트 추가. pytest 실행 체계는 준비 작업에서 정비 |
| 문서 조회 | 모니터링 알림 키워드로 유형을 골라 MCP로 Runbook 파일을 읽음 | 증상·점검 결과를 이용한 임베딩 검색과 근거 기반 생성으로 확장 |
| LangSmith | 서버·그래프·LLM·MCP에 추적 코드가 이미 있음 | POST/SSE 요청 추적 연결, 버전·접수·검색 문서·검증 결과 기록, 최종 평가 추가 |
| 답변 검증 | 길이·절차 번호만 검사하고 최대 시도 시 강제 합격. 미검증 초안이 화면에 노출됨 | RAG 연결 시 최소 표시·실패 종료 규칙부터 고치고, 5단계에서 근거 검증 강화 |

모듈화를 새 1단계로 잡아 기존 단계 번호를 다시 매기지 않는다. 작은 준비 작업과
2~6단계 기능 변경 안에 포함한다. RAG를 4단계로 앞당기고, 그 근거를 검사하는 기능을
5단계에서 완성한다. 이미 작성된 과거 기록은 당시 계획을 보존하며, 향후 순서는 이 문서를 따른다.

`agent/` 아래 신규 파일 이름은 설계 기준이며 실제 변경 범위에 맞춰 최소한으로 만든다.
`server.py`는 HTTP 요청과 응답, `graph.py`는 처리 순서와 분기를 맡도록 정리한다.
공통 요청 준비·저장 처리가 커지면 `agent/chat_service.py`로 추출해 POST와 SSE가 함께 사용한다.
LLM·MCP·DB 연결 생성은 기존 lifespan에서 하고, 내부 함수가 요청마다 새 연결을 만들지 않게 한다.

2단계는 저장 기능을 처음 만드는 작업이 아니다. 현재 실행 스크립트의 `rm -f session.db`를
제거하고, 브라우저에서 대화를 다시 식별하며, 기존 메시지를 유지한 채 접수 테이블을
추가하는 작업부터 한다. 전송 중 끊김·재시도·저장 실패가 중복 접수나 잘못된 완료 표시를
만들지 않도록 POST/SSE의 저장 시점을 정하고 테스트한다. thread ID는 인증 수단으로 쓰지 않는다.

## 3. 자연어 문의가 처리되는 흐름

예시: 사용자가 `auth-service`를 선택하고 “오전 9시부터 로그인 후 화면이 넘어가지 않아요.
오류 메시지는 없어요.”라고 입력한다.

1. 문의 원문과 선택 시스템을 접수 ID에 연결해 저장한다.
2. 증상·발생 시각·오류 메시지·사용 환경을 추출하고 기존 접수 정보와 합친다.
3. 모르는 정보만 짧게 추가 질문한다. 모든 항목이 채워질 때까지 기본 점검을 막지는 않는다.
4. MCP로 선택한 시스템을 점검하고, 증상과 관측 결과로 관련 FAQ·Runbook을 검색한다.
5. 관측 사실·문서의 일반 안내·추가 확인 사항을 구분해 답변하고 근거를 검증한다.
6. 결과를 저장하고 관리자 화면은 같은 저장 데이터로 접수 요약을 보여준다.

접수 필드는 `미언급`, `없음`, `모름`, `값 있음`을 구분한다. “오류 메시지 없음”은
누락으로 취급하지 않는다. “오전 9시”는 원문을 보존하고 날짜·시간대를 임의로 확정하지 않는다.
선택 시스템은 LLM 추출 결과로 바꾸지 않는다. 대화 중 다른 시스템을 선택하면 새 문의로
분리하는 것을 기본으로 하여 이전 점검 결과가 섞이지 않게 한다.

관리자 요약은 LLM에게 새로 추측시키기보다 저장된 필드와 점검·검색 결과로 구성한다.
이메일·Slack 전송은 포함하지 않으며, 우선 로컬 관리자 목록·상세 화면을 만든다.
사내 배포 시 필요한 인증과 관리자 권한 검사는 로컬 시연 범위와 구분한다.

## 4. RAG 최소 구현 범위

문서 준비 흐름은 `FAQ·Runbook → 문서 분할 → 임베딩 → 로컬 색인 저장`으로 한다.
요청 흐름은 `증상·선택 시스템·관측 결과 → 검색 → 관련 근거 → 답변 생성·출처 표시`다.
이처럼 검색 결과를 생성 문맥에 전달하는 구성을 구현한다.
([LangChain 공식 검색·RAG 설명](https://docs.langchain.com/oss/python/deepagents/retrieval))

- 기존 Runbook 6개를 활용하고 로그인·결제 등 사용자 FAQ를 별도 작성한다.
- 문서와 청크에 `document_id`, `chunk_id`, 제목, 용도(`user`/`operator`), 적용 시스템,
  파일 경로, 문서 버전을 둔다. 공통 문서와 시스템 전용 문서의 검색 범위를 구분한다.
- 최초 검색은 상위 3개 후보를 기본으로 시작한다. 점수 기준은 개발용 질문으로 조정하고,
  모든 질의에서 무조건 3개를 사용하지 않는다. 관련 근거가 없으면 없다고 반환한다.
- 사용자 안내에는 사용자용 자료를 사용하고 운영자 조치 절차는 관리자 자료로 구분한다.
  운영 문서 내용이 사용자용 답변 문맥에 무조건 섞이지 않도록 검색 단계에서 용도를 제한한다.
- 임베딩 모델과 색인 구현은 한국어 예제 검색·로컬 실행 가능성을 확인해 4단계에서 확정한다.
  별도 원격 벡터 DB 서버부터 만들 필요는 없다. 검색기 인터페이스는 교체 가능하게 둔다.
- 임베딩·문서 버전을 저장하여 문서나 모델이 바뀌면 색인을 재생성한다. 매 질문마다 전체
  문서를 다시 임베딩하지 않는다. 생성한 색인·캐시·모델 파일은 Git에 올리지 않는다.
- 빈 검색 결과, 검색 시스템 오류, 관측 데이터 부족을 서로 다른 상태로 처리한다.
  의미가 비슷한 매뉴얼을 찾았다는 이유로 실제 장애 원인을 확정하지 않는다.
- 단위 테스트의 고정 벡터/가짜 검색기는 분기 검사용이다. 실제 의미 검색 성능은 실제
  임베딩을 사용하는 별도 평가로 확인한다. FAQ가 늘어난 효과와 검색 방식 효과도 구분한다.

4단계에서는 기존 답변의 강제 합격과 미검증 초안 표시를 먼저 정리해 RAG 결과를 연결한다.
5단계는 여기에 실제 출처 ID 존재 여부, 인용과 검색 결과 연결, 관측 수치·시스템 일치,
근거 부족 시 표현 규칙을 더한다. 규칙 검사로 모든 환각을 탐지한다고 주장하지 않는다.

## 5. 테스트와 LangSmith는 함께 준비한다

기존 17개 검사는 그대로 유지한다. `pytest`는 기존 `unittest.TestCase`도 수집할 수 있으므로
전부 재작성하지 않고 신규 모듈의 단위 테스트부터 추가한다. 개발 의존성·실행 명령은 준비
작업에서 분리하고 실제 실행으로 호환성을 확인한다.
([pytest 공식 문서](https://docs.pytest.org/en/stable/how-to/unittest.html))

| 검사 종류 | 대상 | 실행 방식 |
|---|---|---|
| 단위 테스트 | 접수 병합, 문서 필터, 출처 검사, 재작성 종료 | 임시 DB·고정 데이터·가짜 LLM/검색기. 외부 서비스 없이 실행 |
| 통합 테스트 | API→그래프→저장, SSE/POST 일치, 프록시, 관리자 조회 | 테스트 서버·임시 DB. 실제로 연결한 부분과 대체한 부분을 명시 |
| 품질 평가 | 실제 한국어 의미 검색, 최종 답변의 근거 일치 | 고정 평가 질문·실제 임베딩/LLM·고정 샘플 점검 데이터 |

LangSmith는 이미 있는 추적을 활용하되, 새 노드를 만들 때 접수 ID·요청 ID·선택 시스템·
코드 버전·모델·문서 버전·검색된 문서 ID·검증 결과·오류·소요 시간을 연결한다.
POST의 `_handle_chat()`과 웹의 SSE는 현재 실행 경로가 다르므로 양쪽의 요청 단위 추적과
run ID 전달을 맞춘다. 이를 위한 공통 처리가 필요할 때 `agent/observability.py`로 추출한다.
태그와 메타데이터를 통한 실행 구분은 공식 기능을 활용한다.
([LangSmith 공식 문서](https://docs.langchain.com/langsmith/add-metadata-tags))

추적 코드를 넣는 것, 외부 서비스에 실제 수집되는 것, 정답 데이터로 평가하는 것은 각각
별도 완료 항목이다. 기본 자동 테스트는 외부 추적을 끄고, 수집 검증은 합성 문의만 사용한다.
외부 추적이 꺼져도 접수·검색·응답 기능은 동작하도록 한다. 실제 API 키나 대화 DB는 커밋하지 않는다.
이 설계 검토에서는 실제 키·연결 상태를 확인하거나 LangSmith에 데이터를 전송하지 않았다.

## 6. 전후 비교 설계

최종 캡처는 6단계 완료 후 진행한다. 다만 평가 사례와 정답 기준은 구현 전에 준비한다.
초기에는 개발용 10개·최종 확인용 10개 등 합성 문의 20개 정도로 시작하고, 결과는 표본 수와
함께 제시한다. 설정·문턱값은 개발용 사례로 조정하고 최종 확인용 사례 결과를 별도 보고한다.

사례에는 동일 뜻의 다른 표현, 복수 장애 가능성, 문서가 없는 질문, 정상 시스템,
정보 누락, 명시적 “없음”, 후속 답변, 조회 실패를 포함한다. 다중 턴 사례는 질문 하나가
아닌 전체 대화 순서와 기대 접수 상태를 기록한다. 해당하지 않는 지표의 분모에는 넣지 않는다.

| 비교 지표 | 판정 기준 |
|---|---|
| Hit@3 | 정답 문서가 있는 검색 질문 중 상위 3개에 정답 문서가 하나 이상 있는 비율 |
| Recall@3 | 정답 문서가 여러 개면, 질문별 정답 집합 중 상위 3개가 회수한 비율을 평균 |
| 근거 부족 처리율 | 정답 문서가 없는 검색 질문 중 무관한 안내를 만들지 않고 근거 부족을 반환한 비율 |
| 접수 정보 일치 | 추출·병합한 필드가 정답 상태 및 사용자 원문과 일치하는지 확인 |
| 잘못된 답변 차단·정상 답변 오차단 | 의도적으로 잘못된 답변의 차단과 정상 답변의 잘못된 거부를 함께 측정 |
| 응답 시간 | 전체 시간과 검색·생성 시간을 구분해 반복 측정. 평균·중앙값·표본 수와 실행 조건 기록 |
| 근거 일치 | 관측 사실·문서 인용·원인 추정이 기준에 맞는지 고정 기준으로 사람이 확인 |

정답이 하나인 경우 Hit@3와 Recall@3는 같지만, 여러 정답 중 하나만 찾은 비율을 일반적인
Recall@3라고 부르지 않는다. 원본은 단일 Runbook을 고르는 방식이므로 실제 선택 결과를
그대로 평가하고 임의로 상위 3개 후보를 만들어 주지 않는다.

전체 서비스 비교는 `원본 ee32f7e ↔ 6단계 완료 커밋`으로 한다. RAG 효과를 따로 보일 때는
같은 문서 집합·같은 질문에서 기존 규칙 검색과 의미 검색을 비교한다. 원본에 없던 FAQ를
추가한 효과까지 임베딩 정확도 향상으로 합산하지 않는다. 모델·프롬프트·임베딩·데이터 버전,
동시 요청 수·캐시·재시도·교육용 인위 지연 설정을 기록한다.

현재의 fake LLM, MCP 무작위 값, 첫 요청 실패 시뮬레이션을 실제 서비스 성능의 증거로
쓰지 않는다. 최종 품질 평가에서는 통제된 점검 데이터와 실제 모델 사용 여부를 명시한다.
LangSmith의 데이터셋 기반 평가도 별도 정답과 평가기가 필요하다.
([LangSmith 공식 평가 설명](https://docs.langchain.com/langsmith/evaluation-types))

## 7. 단계마다 Git에서 다시 찾는 방법

각 단계는 `코드 + 관련 테스트 + doc/step_XX_*.md 변경 기록`을 함께 커밋하고 push한다.
문서에는 수정 이유, 변경 파일, 기존/이후 동작, 테스트 결과, 남은 한계를 짧게 적는다.
