# AI 헬프데스크 개선 기획·분석 보고서

발표 자료로 옮기기 위한 설명이다. **구현 효과**, **실제로 측정한 값**, **향후 활용**을 구분한다.
커밋·원시 결과·화면은 [최종 실행 근거](evidence/final/README.md)에 연결한다.

이 보고서의 실측 값은 **1~6단계 Ollama 완료본** 기준이다. 후속
[7단계 OpenAI 임베딩 선택](step_07_openai_embeddings.md)은 별도로 기록하며,
[새 실제 비교 결과](evidence/embedding_comparison/RESULTS.md)는 이전 성과와 구분한다.
이 비교에서 OpenAI API 연결은 성공했지만 검색 품질·속도 우위는 확인되지 않았다.

## 1. 기존 코드는 무엇을 하는 코드였나

원본 `ee32f7e`는 FastAPI·LangGraph·MCP·Vue를 연결하는 운영 인시던트 실습 코드다.
질문을 일반 대화/점검으로 분류하고, 점검 작업을 계획하며, 샘플 모니터링 지표와
키워드로 고른 Runbook을 읽어 답변한다. 재시도·병렬 처리·검증 루프를 학습할 수 있다.
LangSmith 추적과 SQLite 메시지 저장도 원래 존재했다.

원본은 현재 문서를 임베딩으로 찾는 RAG 검색기가 없었다. 데이터는
`data/monitoring.json`, `data/runbooks/`에 미리 준비한 샘플이며 실제 사내 서버를 관측하지 않는다.

## 2. 어떤 문제가 있었나 — 기존 코드

원본 `agent/graph.py`의 검증 기준은 다음과 같았다.

```python
ok = len(draft) >= 30 and "1)" in draft
verdict = "합격" if ok else "불합격"
if not ok and attempts >= 3:   # 실모델 무한 재작성 방지 — 최대 3회 후 통과 처리
    ok, verdict = True, "합격(최대 시도 도달 — 통과 처리)"
```

형식이 맞아도 수치·출처·대상이 틀릴 수 있고, 3회 실패한 초안도 합격으로 바뀌었다.
또한 작성 중 `AnswerToken`을 보내므로 검증이 끝나기 전에 초안이 화면에 표시됐다.

기존 `sh/run_agent_ollma.sh`에는 다음 줄이 있었다.

```bash
rm -f session.db
```

DB 저장 코드가 있더라도 실행 스크립트에서 DB를 지우면 기록을 이어가기 어려웠다.
그 밖에 화면의 명시적 시스템 선택, 구조화된 문의 접수, 임베딩 검색, 관리자 목록이 없었다.

## 3. 사용자·관리자에게 어떤 영향을 줬나

| 문제 | 사용자 영향 | 관리자 영향 |
|---|---|---|
| 자연어 분류·대상 추측에 의존 | 같은 증상도 표현에 따라 점검 경로를 타지 않을 수 있음 | 어떤 시스템을 확인했는지 재확인 필요 |
| 재시작·새 대화 때 기록 연결 부족 | 설명을 반복하거나 결과를 잃을 수 있음 | 문의와 후속 답변을 한 접수로 보기 어려움 |
| 증상·시간·오류·환경이 원문에만 존재 | 무엇을 더 알려줘야 하는지 불명확 | 원문에서 필요한 정보를 다시 정리 |
| 키워드 기반 매뉴얼 선택 | 다른 표현의 관련 문서를 놓칠 수 있음 | 관련 근거를 직접 찾아야 함 |
| 형식 검사·검증 전 초안 노출 | 근거 없는 수치를 확정 정보로 오인 가능 | 잘못된 안내를 검토하고 바로잡는 부담 |

## 4. 어떻게 개선하기로 했나

`시스템 선택 → 원문 저장 → 자연어 접수 → MCP 샘플 점검 → RAG 검색 → 답변 검증 → 저장 → 관리자 확인`.

기존 LangGraph 흐름과 `SupervisorDeps`를 유지하면서 책임별 모듈을 추가했다.
RAG는 사용자 FAQ와 운영자 Runbook을 따로 검색하고, 직원용 답변에는 사용자 문서만 전달한다.
외부 장애 분석 에이전트를 여러 개 만드는 대신 단일 흐름의 근거·기록·검증을 보완했다.

## 5. 실제 반영 사항 — 파일과 코드

| 단계 | 주요 파일 | 바뀐 동작 |
|---|---|---|
| 1 | `system_catalog.py`, `server.py`, `graph.py`, `web_chat.html` | 목록에 있는 시스템만 선택하고 빈 입력 차단 |
| 2 | `session_store.py`, `inquiry_store.py`, `chat_service.py`, 실행 스크립트 | DB 유지·접수 상태·같은 요청 재전송·저장 후 응답 |
| 3 | `intake.py`, `intake_llm.py`, LLM 어댑터, `graph.py` | 자연어의 네 필드 추출·원문 확인·후속 답변 병합 |
| 4 | `retrieval.py`, `answer_generation.py`, `data/faq/`, `knowledge_catalog.json` | 실제 로컬 임베딩 검색·출처·근거 없음/검색 실패 구분 |
| 5 | `answer_validation.py`, `graph.py` | 대상·수치·인용·명백한 단정 검사, 실패 시 제한된 안내 |
| 6 | `inquiry_summary.py`, `web_admin.html`, `observability.py`, `evals/evaluate.py` | 관리자 조회·버전별 추적·고정 질문 평가 |

선택 대상은 LLM에 다시 추측시키지 않는다. `graph.py`에서 직접 작업을 만든다.

```python
selected = validate_selected_system(state["selected_system"])
tasks = [{"id": "task-0", "agent": "research", "kind": "monitoring",
          "target": selected, "status": "pending"}]
```

검증 실패 횟수를 채웠다는 이유로 합격시키지 않는다.

```python
ok = checked["ok"]
verdict = "합격" if ok else "불합격"
exhausted = not ok and attempts >= 3
if exhausted:
    verdict = "추가 확인 필요(검증 실패)"
```

계속 실패했다면 마지막 초안 대신 확인된 정보로 제한한 답변을 만든다.

```python
if state.get("validation", {}).get("status") == "fallback":
    from .answer_generation import evidence_fallback
    final = evidence_fallback(state.get("selected_system"), state.get("collected", []))
```

관리자는 저장된 완료 요청의 근거를 읽는다. 새로운 실패 요청이 있으면
`evidence_is_current=false`로 이전 결과임을 표시한다. 관리 화면 조회가 LLM을 다시 호출하지 않는다.

## 6. 이전과 지금 — 관찰 결과

| 비교 | 이전 | 현재 |
|---|---|---|
| “로그인 후 화면이 넘어가지 않아요” | fake 모델에서 일반 대화로 분류, 점검 없음 | auth-service 선택 시 해당 샘플 점검과 관련 FAQ 조회 |
| “오전 9시부터요. Chrome을 사용하고 있어요.” 후속 답변 | 접수 필드 병합 기능 없음 | 이전 증상·오류 없음 유지, 시간·환경 추가 |
| 재전송 | 접수 요청 ID에 의한 결과 재사용 없음 | 같은 ID의 완료 요청은 저장 결과 반환, 도구 재호출·메시지 중복 없음 |
| 관리자 확인 | 별도 화면 없음 | 접수 목록·원문·관측·두 종류 문서·검증 상태 조회 |

최종 확인용 검색 질문은 설정을 고정한 뒤 한 번 실행했다.

| 검색 측정 | 기존 규칙 어댑터 | 의미 검색 |
|---|---|---|
| 같은 Runbook 정답 질문 4건 | 정답 포함 1/4 | 상위 3개 정답 포함 4/4 |
| Runbook 정답 없는 질문 1건 | 기본 문서를 반환, 구분 0/1 | 근거 없음 1/1 |
| 새 FAQ 정답 질문 6건 | 기능 없음·비교 제외 | 상위 3개 정답 포함 6/6 |
| FAQ 정답 없는 질문 1건 | 비교 제외 | 근거 없음 1/1 |

이 수치는 소수 합성 검색 질문에 대한 결과다. 다른 후보의 관련성, 실제 LLM 답변 품질,
실제 장애 원인 정확도를 100%라고 주장할 수 없다. 규칙 어댑터는 동일 문장을 합성 알림으로
입력한 검색 방식 비교이며 원본 전체 서비스 측정과 다르다.

Runbook 의미 검색 평균 약 0.028초(5회), FAQ 평균 약 0.187초(7회)였다.
색인 준비 뒤 순차 실행했으며 모델의 완전한 cold start를 통제하지 않았다.
기존 문자열 규칙보다 처리 비용이 추가되므로 속도가 개선됐다는 주장은 하지 않는다.

원본·완료본 실제 화면, HTTP 흐름 검사, LangSmith 수집·후속 보완 기록은
[최종 비교 자료](evidence/final/README.md)에 따로 보존한다. 자동 테스트 통과 수는 장애 진단 정확도가 아니다.

실제 기본 모델(`qwen3:0.6b`/`qwen3:8b`)도 합성 문의로 실행했다. 통합 검사와 실제 모델 실행 과정에서 정상 FAQ의
부정 표현, 샘플 알림의 연결 풀 비율, `1.` 번호 목록을 오차단하는 검증 규칙을 발견해
각각 회귀 테스트와 별도 커밋으로 고쳤다. 최종 한 건은 첫 답변 검증에 통과했고 그래프 실행은
48.70초였다. 앞선 실패 실행과 조건·출력·재작성 횟수가 달라 속도 개선율로 계산하지 않는다.
접수 추출은 소형 모델이 실패해 원문 기반 규칙으로 전환했으므로 LLM 추출 성공으로 주장하지 않는다.
전체 137개 자동 테스트와 17개 실제 HTTP 흐름 검사가 통과했다.

## 7. 현재 성능으로 어디에 활용할 수 있나

**사내 IT 헬프데스크 접수 보조:** 직원은 양식 대신 자연어로 문의하고, 서비스가 증상·시각·
오류·환경을 정리한다. 관리자는 원문과 근거를 보고 필요한 추가 질문을 줄일 수 있다.
실제 업무 시간 절감량은 향후 사용자 실험으로 측정해야 한다.

**배포 후 상태 점검 보조의 기반:** 시스템 선택·접수 기록·문서 검색·검증·추적을 재사용할 수 있다.
실제 배포 후 점검 도구로 쓰려면 운영 모니터링·배포 이력·오류 로그를 연결해야 한다.
현재는 실제 배포 성공 여부나 오류 원인을 판정하지 않는다.

운영 전 추가 범위는 인증/권한, 실제 데이터 연동, 문서 최신화, 충분한 실제 문의 평가다.
자동 복구·Slack 전송·Multi-Agent는 이번 구현 범위에 포함하지 않았다.
